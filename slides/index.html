Understanding the Technology

What is AWS Lambda?

"Serverless" compute — on-demand function execution

  • Write a function, upload it to AWS, and it runs only when triggered
  • No servers to provision or manage — AWS handles all infrastructure
  • You pay only for compute time actually used, measured in milliseconds
  • Ideal for sporadic queries and bursty research workloads

Cost advantage: Traditional EC2 runs 24/7 whether you use it or not. Lambda runs only when invoked — perfect for lightweight, event-driven tasks.

Know the Boundaries

What Lambda is NOT Good For

15-Minute Execution Limit

Lambda kills your function after 15 minutes — no exceptions.

Not suitable for batch compute, HPC, or long-running simulations.

Cold Start Latency

First invocation can take seconds to spin up, especially with container images.

Impacts interactive applications where milliseconds matter.

Package Size Constraints

Scientific Python libraries are large — NumPy, Pandas, SciPy quickly exceed limits.

Container images help, but add Docker/ECR complexity.

"Serverless" ≠ "run any analysis without thinking about infrastructure" — Lambda fills a specific niche.

The Entry Point

The Handler Function

import os, json from snowexsql import db def lambda_handler(event, context): # Fetch database credentials from Secrets Manager secret = _get_secret(os.environ['DB_SECRET_NAME']) # Write temporary credentials file _write_temp_credentials(secret, '/tmp/credentials.json') # Connect to database using credentials engine, session = db.get_db('/tmp/credentials.json') # Execute query based on event action action = event.get('action') result = _handle_action(action, event, session) # Return JSON response return { 'statusCode': 200, 'body': json.dumps(result) }

Secrets Manager

No hardcoded passwords! Credentials are fetched securely from AWS Secrets Manager at runtime

Temporary Credentials

Writes credentials to /tmp/ for the duration of this invocation — never stored permanently

Database Connection

Uses snowexsql package's db.get_db() with credential file — same code works locally and in Lambda

Action Handling

Event specifies action (query type), handler delegates to appropriate method, returns JSON

Why AWS IAM?

  • No credential distribution: Users authenticate with their own AWS credentials, not shared database passwords
  • Audit trail: Every Lambda invocation is logged in CloudTrail with the IAM identity
  • Granular permissions: Fine-grained control through IAM policies (who, what, when, from where)
  • Automatic rotation: AWS access keys can be rotated; temporary credentials expire automatically
  • Defense in depth: Function URL is useless without valid AWS credentials + IAM permission

CloudBank Platform

Setting Up Lambda on CloudBank

IAM Permissions

  • Request permissions for Lambda, ECR, API Gateway, and Secrets Manager
  • Work with your CloudBank point of contact to obtain the required roles
  • Follow least-privilege — request only the services your project needs
  • Assign an execution role to the Lambda function granting Secrets Manager read access

CloudBank uses AWS Organizations — your account may inherit default permission boundaries

Credit Usage

  • Lambda: pay per invocation — typically fractions of a cent per query
  • ECR: ~$0.10/GB/month for container image storage
  • EC2: the database instance is the primary ongoing cost — stop it when not in use
  • Monitor spend with AWS Cost Explorer and set billing alerts

CloudBank credits cover most research use; consult your allocation before scaling up

Account Gotchas

  • Lambda and EC2 must be in the same AWS region
  • Configure security groups: Lambda needs outbound access to the database port (5432 for PostgreSQL)
  • CloudBank accounts may have region restrictions — confirm with your administrator
  • Container image architecture must match Lambda config (x86_64 vs arm64)

Test with a minimal query first to validate end-to-end connectivity before building out the full API
