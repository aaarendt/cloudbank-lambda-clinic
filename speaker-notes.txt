SLIDE 2: 02 Research Problem
========================================================================

Let me start with the motivating example. SnowEx was a NASA field campaign that ran from 2017 to 2023, sending teams into the field to measure snow depth, density, and other properties across a range of landscapes and snow types. The goal was to collect ground truth data that could be used to validate airborne and satellite remote sensing instruments. The datasets are highly structured — measurements tied to specific locations, dates, instruments, and observers — which makes them a perfect fit for a relational database. And once the data is in a database, the question becomes: how do collaborators access it? That's where Lambda comes in.

========================================================================
SLIDE 3: 03 Database
========================================================================

So what exactly lives in this database? We built the SnowEx database using PostgreSQL with the PostGIS spatial extension, which means we can store point locations, run geographic queries, and do spatial joins. The database contains multiple tables — one for snow depth measurements, another for density pits, another for spectral reflectance data — and they're all linked by common keys like site name, date, and geographic coordinates. Each table has its own schema with metadata fields describing the instrument, the observer, and the measurement protocol. The result is a normalized relational structure that allows researchers to query across campaigns, compare sites, and pull just the subset of data they need for their analysis. This is the kind of database that lives on an EC2 instance and needs a clean API layer on top of it, which is exactly what Lambda provides.

SLIDE 4: 04 Access
========================================================================

Now let's talk about database access. Our first implementation required users to install a command-line client on their local machine and distribute AWS credentials to everyone who needed access. This worked, but it had serious problems. Managing credentials is a security headache — you're handing out keys that, if compromised, could expose your entire database. And it put a burden on users to configure their local environment correctly. What we needed was a way to provide secure, passwordless access without distributing credentials. That's the problem Lambda solves. By putting Lambda in front of the database with API Gateway, users can query through a simple web API without ever touching credentials. The architecture diagram on the right shows how this works — API Gateway handles authentication, Lambda executes the query, and users get their data back without needing direct database access. It's a much cleaner, more secure pattern.

========================================================================
SLIDE 5: 05 Lambda Overview
========================================================================

So what exactly is AWS Lambda? Lambda is Amazon's serverless compute service. Now, the term serverless can be misleading — there are still servers involved. What it really means is that you don't have to provision, manage, or pay for servers when they're idle. With traditional EC2 instances, you spin up a virtual machine and it runs continuously whether you're using it or not. With Lambda, you write a function, upload it to AWS, and it only runs when triggered. Each invocation spins up a fresh execution environment, runs your code, and then shuts down. You only pay for the compute time you actually use, measured in milliseconds. For research workflows where you have sporadic queries or bursty workloads, this model can be much more cost-effective than keeping an always-on server running. Lambda was designed for exactly this kind of use case — lightweight, event-driven tasks that don't need persistent infrastructure.

========================================================================
SLIDE 6: 06 Applications
========================================================================

Lambda really shines in three main scenarios. First, you can use it for data processing pipelines. A researcher uploads a new file to S3 — maybe a satellite image or a batch of sensor data — and that upload event automatically triggers a Lambda function that processes the file, extracts metadata, or kicks off a workflow. You never had to think about scaling or managing servers. Second, Lambda works beautifully as an API layer, which is exactly what we're doing with the SnowEx database. API Gateway receives a query request, hands it to Lambda, Lambda connects to the database, runs the query, and returns the results. It's clean, stateless, and scales automatically. Third, Lambda can act as the glue between services — responding to events from CloudWatch, SNS, EventBridge, or any other AWS service. The common thread across all of these is that they're event-driven, relatively short-running tasks where you don't want the overhead of managing infrastructure. Lambda is perfect for this middle ground between one-off scripts and full application deployments.

========================================================================
SLIDE 7: 07 Limitations
========================================================================

Now let's talk about what Lambda is not good for — because understanding the constraints is just as important as understanding the capabilities. Lambda has a hard fifteen-minute execution limit. If your function hasn't finished by then, AWS kills it. That means Lambda is not a replacement for batch compute jobs or HPC workloads. If you're running a multi-hour climate simulation or training a deep learning model, Lambda is the wrong tool. Second, there's cold start latency. When a Lambda function hasn't been invoked recently, AWS has to spin up a fresh execution environment, and that can take anywhere from a few hundred milliseconds to several seconds, especially if you're using container images with large dependencies. For interactive applications where every millisecond counts, that delay can be a problem. Third, packaging scientific Python dependencies is non-trivial. Libraries like NumPy, Pandas, and SciPy are large, and if you go down the rabbit hole of geospatial or machine learning libraries, you quickly hit Lambda's package size limits unless you use container images. And even then, you're dealing with Docker and ECR, which adds complexity. The key point here is that serverless does not mean you can run any arbitrary analysis without thinking about infrastructure. Lambda fills a specific niche — lightweight, event-driven tasks — and if your workload doesn't fit that profile, you need a different tool.

SLIDE 9: 09 Containers
========================================================================

So why do we need container images for the SnowEx database? The answer comes down to package size. When you're working with scientific Python, you're not dealing with lightweight libraries. NumPy alone is tens of megabytes. Add Pandas for data manipulation, SQLAlchemy for database connections, GeoAlchemy2 for spatial queries, and you're well over the 50-megabyte zip file limit that Lambda imposes. And that's before you even write your own code. The zip approach that works great for hello world functions simply doesn't scale to real scientific workloads. So what's the alternative? Container images. Instead of zipping up your Python code and dependencies, you write a Dockerfile — the same tool you'd use for any containerized application — install your dependencies normally using pip or conda, build the image, push it to AWS Elastic Container Registry, and point your Lambda function at that image. Lambda pulls the image and runs it just like it would run a zip file, but now you have 10 gigabytes of space instead of 50 megabytes. This isn't a workaround or a hack — it's the modern, recommended way to deploy Lambda functions with heavy dependencies. AWS built this capability specifically for use cases like ours.

========================================================================
SLIDE 10: 10 Handler
========================================================================

Now let's look at what the actual Dockerfile looks like for the SnowEx Lambda function. If you've never seen a Dockerfile before, think of it as a recipe — a list of instructions that tells Docker how to build your container image. The first line specifies the base image. AWS provides official Lambda base images for Python, so we start with that. It already has the Lambda runtime configured, which saves us a lot of setup. Next, we copy our requirements file into the image and run pip install to download all our Python dependencies — NumPy, Pandas, SQLAlchemy, GeoAlchemy2, all the libraries we need. Then we copy our actual function code into the image. Finally, we tell Lambda which function to invoke when the container runs. That's it. This Dockerfile is available in the SnowEx GitHub repository, and you can use it as a template for your own database query functions. The key thing to notice is that this looks almost identical to any Python Dockerfile you'd write for a web app or a data pipeline — Lambda's container support uses standard Docker tooling, which means you can leverage existing knowledge and workflows.

========================================================================
SLIDE 11: 11 Dockerfile
========================================================================

Now let's look at the actual Python code that runs inside the Lambda function — the handler. This is where the real work happens. When API Gateway receives a query request, it packages that request into an event object and passes it to this handler function. The handler takes two arguments. The first is event, which contains all the incoming data — in our case, that's the database query parameters sent by the user. The second is context, which gives you runtime information like how much time you have left before Lambda times out. We start by parsing the query parameters from the event. Then we use SQLAlchemy to connect to our PostgreSQL database on EC2. We execute the query, fetch the results, and return them as JSON. Lambda automatically handles the HTTP response, so we just return a dictionary with a status code and a body. The key point here is that this is just normal Python. You're not learning a new framework or a proprietary API. If you can write a function that connects to a database and returns JSON, you can write a Lambda function. The only Lambda-specific part is the function signature — event and context — and even that is straightforward once you see it once.

========================================================================
SLIDE 12: 12 Deploy ECR
========================================================================

Now that we have our Dockerfile and handler code, we need to build the container image and push it to AWS. This is where ECR comes in — Elastic Container Registry. Think of it as Docker Hub, but inside your AWS account. The deployment process has three main steps. First, you build the Docker image locally using docker build. This reads your Dockerfile, installs all your dependencies, and packages everything into a container image. Second, you tag the image with your ECR repository URL. This tells Docker where you want to push the image. Third, you push the image to ECR using docker push. Once it's in ECR, Lambda can pull it and run it. I'm not going to execute these commands live because the build step can take a few minutes — we're installing NumPy, Pandas, and all those scientific Python libraries, which takes time. But I want you to see the commands so you know what the workflow looks like. For today's demo, I've already built and pushed an image to ECR, so we can focus on the Lambda configuration and actually querying the database.

========================================================================
SLIDE 13: 13 Access
========================================================================

The last step is making the Lambda function accessible to users. Right now, the function exists inside AWS, but nobody can reach it. It's like having a phone without a phone number. What we need is a way for researchers to send queries from their laptop, from a Jupyter notebook, from anywhere, and have those queries reach the Lambda function. AWS makes this simple — they give your Lambda function a web address, just like any website has a URL. You enable this feature in the Lambda console, and AWS hands you an HTTPS URL. Now anyone with that URL can send a query. Of course, you don't want just anyone querying your database, so you set access controls. You can make it completely public, you can require a password, or you can require AWS credentials. For SnowEx, we require AWS credentials, which means only people we've granted permission can run queries. Once that's set up, the workflow is simple. A researcher sends a query from their Python script. That query goes to the URL. AWS receives it, invokes your Lambda function, the function queries the database, and the results come back. That's it. No servers to manage, no VPN to configure, no SSH keys to distribute. Just a URL.

========================================================================
SLIDE 14: 14 Lambda Client
========================================================================

Now let's look at how a query actually travels from a researcher's notebook to the database. There are two sides to this architecture — the client side, which is everything running on the researcher's laptop, and the server side, which is everything running inside the Lambda container on AWS. On the client side, a researcher calls a method on SnowExLambdaClient — something like client.point_measurements.from_filter with a campaign name and a limit. The client serializes that into a JSON payload and sends it as an HTTPS POST request to the Lambda Function URL. That's all it does. It never touches a database directly. At the AWS boundary, that HTTPS request crosses from the researcher's machine into our Lambda function. The Lambda handler receives the JSON payload, reads the action field to understand what kind of query is being requested, and then invokes the appropriate method from api.py. And here's the key insight I want you to take from this diagram: api.py is the same code that runs when you access the database directly, without Lambda. The SQL query construction, the table joins, the filter logic — none of that is duplicated in the client or in the handler. It all lives in api.py, in one place. Lambda is just the transport layer. Finally, api.py hands the query to SQLAlchemy, which executes it against PostgreSQL running on our EC2 instance, and the results travel back through the same chain in reverse. The researcher gets a pandas DataFrame. The entire round trip is invisible to them — from their perspective, they just called a Python method.

========================================================================
SLIDE 15: 15 Architecture
========================================================================

Now let's step back and look at the complete architecture we've just built. This diagram shows all the pieces working together. First, we have our container image stored in ECR — that's the package we built with our Dockerfile containing all our scientific Python dependencies and our handler code. Second, the Lambda function itself pulls that container image and runs it on demand. When a query comes in, Lambda retrieves database credentials from Secrets Manager, connects to the PostgreSQL database running on EC2, executes the SQL query, and returns the results. Third, we have the Function URL that acts as the entry point — researchers send HTTPS requests to that URL, and AWS IAM authentication ensures only authorized users can invoke the function. Finally, the database itself lives on an EC2 instance with credentials securely managed by Secrets Manager, so we never hardcode passwords. The result is a secure, serverless API that lets researchers query the database without managing any infrastructure or handling credentials themselves. This pattern is transferable — you could use the exact same architecture for genomics databases, climate model outputs, hydrology data, or any other scientific dataset that lives in PostgreSQL. Lambda fills the gap between a quick Jupyter notebook prototype and a full production deployment. It gives you the benefits of cloud infrastructure without the operational overhead.

SLIDE 17: 17 Limitations
========================================================================

Now let's talk about when you need to go beyond the helper methods. The API methods like get_point_measurements work great for standard queries — filtering by campaign, instrument, date, or location. But sometimes you need something more complex. For example, say you want to find the average magnaprobe snow depth within 10 meters of each snow pit on the same day. That's a spatial join using PostGIS functions, combined with a date match and a GROUP BY aggregation. The helper methods can't do that. This is where client.query comes in. You can write raw SQL with full access to PostGIS spatial functions, JOIN across multiple tables, and use aggregate functions like AVG or COUNT. You're still using the Lambda API — same secure, credential-free access — but now you have the full power of SQL and PostGIS. The key thing to understand is that Lambda still has the same constraints. If your query takes more than 15 minutes or returns more than 6 megabytes, it will fail. So raw SQL isn't a magic solution for bulk exports. It's a tool for complex queries that the helper methods don't support. For most use cases, stick with the helper methods — they're simpler and less error-prone. But when you need spatial joins, multi-table queries, or custom aggregations, client.query gives you that flexibility.

Let me step back from the SnowEx specifics and talk about what we have actually built — because the pattern transfers well beyond snow science. The architecture is: a containerized Lambda function that exposes a structured scientific database as a secure, credential-free API that any researcher can query from a notebook. Every element of that description has an analog in other fields. In genomics, the database stores variant call metadata — chromosome positions, p-values, population assignments — while the actual VCF files, which can be massive, stay in S3. Lambda queries the index, not the raw files. The dependency stack — BioPython, pysam, scikit-bio — exceeds Lambda's zip limit immediately, which makes container deployment not just useful but necessary. And the security argument is actually stronger here than in SnowEx: distributing credentials to a multi-institution genomics consortium is precisely the problem IAM authentication solves. Climate science follows the same pattern — a CMIP6 model run catalog in PostgreSQL, with actual NetCDF output on an EC2 data volume. Lambda returns a sliced DataFrame. The library stack — xarray, cartopy, cfgrib — is container-only. Hydrology is the most direct transfer: the PostGIS spatial query from the previous slide, ST_DWithin plus a date filter plus a threshold condition, is literally the same query shape you would use for stream gauge networks and watershed boundaries. No architectural change at all. And remote sensing maps naturally onto a STAC catalog backed by PostgreSQL — Lambda returns filtered scene lists as S3 URLs, and an optional second Lambda call extracts pixel statistics from Cloud Optimized GeoTIFFs. The library stack — rasterio, GDAL, pystac — requires container deployment. The cross-cutting message across all four disciplines is this: the container solves the same size problem everywhere. Credential distribution is a universal research pain point. The query shape — small, filtered result from a large structured dataset — is the same in every field. And the gap Lambda fills is always the same gap: between a notebook on your laptop and a full production deployment that your research workflow probably never needs to become.

SLIDE 19: 19 CloudBank Setup
========================================================================

Now let's talk about what's specific to running this on a CloudBank account, because there are a few things that differ from a standard personal AWS account. The first is IAM permissions. CloudBank uses AWS Organizations, which means your account sits inside an organizational structure and may have default permission boundaries applied. You'll need permissions for Lambda, ECR, API Gateway, and Secrets Manager — and you'll need to assign an execution role to your Lambda function so it can read from Secrets Manager at runtime. Work with your CloudBank point of contact to request those roles. The second area is credit usage. Lambda itself is remarkably cheap — you're typically paying fractions of a cent per query. ECR storage is about ten cents per gigabyte per month. The real ongoing cost is your EC2 instance hosting the database, so get in the habit of stopping it when you're not actively using it. AWS Cost Explorer is your friend here — set a billing alert so you don't get surprised. Third, there are a few account-specific gotchas worth knowing. Lambda and your EC2 database instance must be in the same AWS region. You'll need to configure security groups so that Lambda's security group has outbound access to port 5432, which is the default PostgreSQL port. CloudBank accounts may also have region restrictions, so check with your administrator before assuming you can deploy to any region. Finally, make sure your container image architecture matches your Lambda configuration — x86_64 is the safe default. My advice is to test with a minimal query end-to-end before you invest time building out the full API. That way you catch connectivity or permission issues early.
